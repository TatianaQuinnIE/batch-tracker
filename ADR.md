# Architecture Decision Records

## 1. Backend language and framework: Python + Flask with plain sqlite3
Date: 2026-10-10
Status: Superseded by [7]
Context: The workshop (2 staff, roughly a few hundred customer feedback submissions a month) needs a small web app with HTML forms and server-rendered pages, backed by SQLite, running as one process in one container. I am most comfortable in Python and must be able to explain every line.
Decision: Python 3 with Flask 3.1, the standard-library sqlite3 module and Jinja templates (bundled with Flask). Each feature domain becomes a Flask Blueprint.
Alternatives considered: Django, rejected because its ORM, admin and migration system are far more than two small tables need and would hide the schema I have to defend in ADR-3. FastAPI, rejected because it is API-first: server-rendered forms would need extra packages plus a separate ASGI server (uvicorn), adding dependencies without a real need.
Consequences: Very few dependencies and nothing hidden, but I write the SQL and the schema creation myself. Blueprints give each domain its own module, which is where the service split in Assignment 2 will happen.

## 2. Two independent feature domains joined only by batch_code
Date: 2026-10-10
Status: Decided
Context: In Assignment 2 the app will be split into separate services, so the batch register and customer feedback must not depend on each other's code or tables.
Decision: Two packages, batches/ and feedback/, each owning its own table, schema setup, business logic (service.py) and Flask Blueprint (routes.py). The only thing that crosses the seam is the batch_code string printed on the product label; feedback never imports from batches or queries the batches table.
Alternatives considered: One shared models module with a foreign key from feedback to batches. Rejected because it makes joins easy now but ties the two domains together: splitting later would mean untangling shared code and a foreign key that cannot exist across two separate databases.
Consequences: Feedback cannot check through a database join that a batch code exists; after the split that check becomes an HTTP call to the batches service. In exchange, each package can be moved into its own service with its own SQLite file without rewriting it.

## 3. Feedback references batches by batch_code text, with no foreign key
Date: 2026-10-11
Status: Superseded by [7]
Context: Customers only know the code printed on the label, and in Assignment 2 the two tables will live in different services with separate databases.
Decision: One SQLite file (DATA_DIR/tracker.db) with two tables owned by different domains: batches (batch_code UNIQUE) and feedback (batch_code TEXT, indexed, no foreign key). Codes are stored upper-case and dates as ISO text (YYYY-MM-DD).
Alternatives considered: feedback.batch_id INTEGER REFERENCES batches(id). Rejected because customers do not know internal ids, and a foreign key cannot cross two databases once the services are split.
Consequences: The database does not stop feedback for a code that does not exist (it could arrive before the batch is registered); an index on feedback.batch_code keeps the per-batch GROUP BY fast. Splitting later means moving one table, not untangling a relationship.

## 4. Test the service logic directly, then the routes through Flask's test client
Date: 2026-10-12
Status: Superseded by [9]
Context: The brief asks for at least 70% coverage on the core logic of both domains. The bugs that would actually hurt the workshop are at the boundaries: a batch exactly 30 days from expiry, a batch at exactly 10% reactions, fewer than 3 reports, seed data loading twice, and the "No, all good" answer being counted as a reaction.
Decision: Unit tests call batches/service.py and feedback/service.py directly against an in-memory SQLite database (the conn fixture) with a fixed date, so boundary cases are exact. Route tests then use Flask's test client with a temporary DATA_DIR to check redirects, validation errors, kept form values and the JSON endpoints. Coverage is measured on the batches and feedback packages (command in README).
Alternatives considered: Only end-to-end route tests, rejected because boundary values are harder to hit precisely and a failure does not point to the function that broke. Browser tests (Selenium/Playwright), rejected because they add heavy dependencies and are slow for an app with no JavaScript.
Consequences: Service logic is fully covered and the tests can move with each service in Assignment 2 unchanged. Left thinner on purpose: templates are only checked for key text, not layout, so a visual regression would not fail the suite; container behaviour is checked by run.sh instead of pytest.

## 5. No login for workshop staff in this version
Date: 2026-10-12
Status: Decided
Context: Customers must be able to report a reaction without creating an account, but the "Workshop view" and the Batches page are meant for the two workshop staff. The app runs locally for one workshop in Assignment 1.
Decision: I deliberately did not build authentication. Every page is open to anyone who can reach the app.
Alternatives considered: Flask-Login with a staff account, rejected for now because it adds a dependency, password hashing, a SECRET_KEY setting and session tests, roughly doubling the scope for a feature nobody needs while the app runs on a laptop. Hiding the staff pages behind a secret URL, rejected because it is security by obscurity.
Consequences: Batch and reaction data is visible to anyone on the network, so this must be fixed before any public deployment. The Assignment 2 split makes it easier: the batches service can sit behind staff-only access while the feedback form stays public.

## 6. The split: batches and feedback services along the ADR-2 seam, joined over HTTP by feedback
Date: 2026-11-19
Status: Decided
Context: Assignment 2 splits the monolith into two services, each with its own container and database, along the seam of ADR-2. At least one user-visible flow must cross the seam server side, and it must keep working in a designed way when the other service is stopped, asleep (scale to zero) or slow.
Decision: The seam held exactly where ADR-2 put it. The batches service owns the batches table and its seed data; the feedback service owns the feedback table. The only thing that crosses is the batch_code string. The cross-seam flow is server side, in feedback: the staff view of feedback (GET /feedback, /feedback/flagged, /feedback/{code}, and the answer to POST /feedback) shows each batch's product name and expiry status next to its reaction rate, so staff can see that the flagged ROS-2608 is the Rosehip face oil and whether it is still on the shelf. Feedback gets these from batches over HTTP: one GET /batches for a list (joined in code by batch_code, not one call per row) or GET /batches/{code} for one summary, through feedback/batches_client.py, with a timeout of BATCHES_TIMEOUT_S (2 s) on every call and the address in BATCHES_URL. When batches does not answer in time, answers 5xx or answers something that is not JSON, feedback degrades: it still returns its own summaries with batch = null, batches_service = "unavailable" and a notice that the UI shows. Writes never depend on batches: a report is saved even if the code is unknown or batches is down, because losing a customer's reaction report is worse than missing a product name (this keeps ADR-7's choice of not enforcing integrity on write). Each service's /health only checks its own database.
Alternatives considered: Joining in the UI (the browser calls both services and matches codes), rejected as the only flow because the brief requires one server-side flow and it would put domain logic in JavaScript on every page; the UI still calls each service for its own domain. Failing with 503 when batches is down, rejected because reaction rates and the flagged list are the important data and they live in feedback's own database. Caching batch details in a feedback table, rejected for now because it needs a copy of another service's data and a way to keep it fresh; it is the next step if batches cold starts make the degraded view common. Retrying the call inside feedback, rejected because when batches is scaled to zero a retry only makes the user wait longer; the UI retries instead (ui/app.js). Rejecting reports for unknown codes, rejected for the reason above.
Consequences: Only two read endpoints of batches are called and only from one place, which suggests the seam is in the right place (many calls would suggest it is not). Codes that batches does not know are shown as "Not a registered batch". On Azure, when batches is scaled to zero, the first feedback page view may show the notice because a cold start takes longer than 2 s; that call also wakes batches, so the next view has the details. The response shapes feedback relies on are in services/batches/openapi.yaml, and feedback's tests check its stub against that document (ADR-9), so a change to batches' Batch schema is caught in CI.

## 7. Data and migrations: one SQL Server database per service, numbered SQL files and my own runner
Date: 2026-11-18
Status: Decided
Context: Assignment 2 replaces the single SQLite file of ADR-3 with one SQL Server database per service (Azure SQL serverless on Azure, one SQL Server container locally). Assignment 1 created its schema with CREATE TABLE IF NOT EXISTS on every boot, which cannot change a table that already holds data. I need versioned, forward-only migrations that run on startup, exactly once each, in a way I can explain line by line.
Decision: Each service has a migrations/ folder of numbered files (001_init.sql, then 002_..., never edited once applied) and a ~60-line runner, migrate.py. On startup, create_app() connects with retries (db.connect_with_retry), creates dbo.schema_migrations if missing, applies every file whose name is not in that table in file-name order, and inserts the file name in the same transaction as the schema change, so a migration is either fully applied and recorded or not at all. A line with only GO splits a file into batches, as in sqlcmd. The data moved with its table: 001_init.sql ports each Assignment 1 table to T-SQL (INT IDENTITY, NVARCHAR with a length, DATE instead of ISO text), and the batches seed.json is still loaded only into an empty table. The Assignment 1 SQLite data was only the seed rows plus test reports, so nothing was exported from it. The driver is pymssql, which ships as a wheel with FreeTDS inside, so the images need no system ODBC packages. Each service connects with its own login (batches_app, feedback_app) that has a user only in its own database, with db_ddladmin (to run its migrations), db_datareader and db_datawriter, not db_owner.
Alternatives considered: Alembic, rejected because it needs SQLAlchemy as well (two dependencies and an ORM layer I do not use, since all my SQL is hand-written) and its autogenerated migrations would be code I did not write. Keeping CREATE TABLE IF NOT EXISTS plus ad-hoc ALTER statements in Python, rejected because nothing would record what has already run, so a second boot could not know whether to apply a change. pyodbc with the Microsoft ODBC driver, rejected because it needs apt repositories and a larger image.
Consequences: What is lost at the seam: feedback.batch_code can no longer even be in the same database as batches.batch_code, so referential integrity is not enforced by SQL Server. It is compensated in code (the feedback service asks the batches service over HTTP, ADR-6) and deliberately not enforced on write, as in ADR-3: a customer can report on a code before staff register the batch. Migrations at startup are only safe because every Container App runs at most one replica with one gunicorn worker; at more replicas two containers could race on the same migration, and I would move migrations to a pipeline step or take an sp_getapplock lock first. Recovery plan for a bad migration in production, since there are no down-migrations: (1) a migration that fails is rolled back by its transaction and is not recorded, so the container fails to start, the old revision keeps serving and the post-deploy health check fails the run; I fix it in a new commit. (2) A migration that succeeds but is wrong is never edited: I write the next numbered migration that corrects it and deploy it through the pipeline. (3) If data was damaged, Azure SQL point-in-time restore (7 days of automatic backups by default) restores the database to a new name from just before the deploy, and I copy the affected rows back or point DATABASE_URL at it.

## 8. Deployment: Azure Container Apps, serverless Azure SQL, a static website, and CD that signs in with OIDC
Date: 2026-11-20
Status: Decided
Context: The system has to run in my own Azure for Students subscription, scale to almost nothing when idle so the credit lasts, and from the first setup on be changed only by the pipeline. IE accounts cannot create service principals, the subscription only allows five regions, and the images are already built and pushed to GHCR by CI (ADR-9).
Decision: Everything is in one resource group, rg-tquinn-ieu2024, in one region from the subscription's allowed list (the SQL server may sit in another allowed region if the free offer is not available in the first). Each service is a Container App (tquinn-ieu2024-batches, tquinn-ieu2024-feedback) in one environment, with external ingress on port 8000, 0 to 1 replicas and 0.25 vCPU / 0.5 GiB: at most one replica, so the migrations that run at startup (ADR-7) never run twice at once. Each service has its own serverless General Purpose database on the free offer (auto-pause after 60 minutes), on one SQL server, and connects as a contained user that exists only in its own database, with db_ddladmin, db_datareader and db_datawriter, so a service cannot read the other's data. The UI is the ui/ folder on a Storage static website (tquinnieu2024ui); its address is the only origin the services allow (ALLOWED_ORIGIN, CORS in Flask, ingress CORS off). The pipeline signs in as a user-assigned managed identity, tquinn-ieu2024-github, with Contributor on the resource group only, through a federated credential for pushes to main (registered with names and with numeric IDs), so no Azure password or key is stored in GitHub. CD (.github/workflows/cd.yml) runs on every push to main: it calls ci.yml with workflow_call, so the deploy job starts only if lint, tests, describe, integration and images passed on the same commit, and CI itself no longer runs on pushes to main. Then it sets each app's database-url secret from the password in GitHub secrets, points each app at ghcr.io/tatianaquinnie/batch-tracker-<service>:<commit SHA> with a new revision, writes ui/config.js with the two Container Apps addresses, uploads ui/ to $web, and waits up to 10 minutes for each /health to answer 200 with the deployed commit as its version, failing the run otherwise. Images are built with provenance: false and the two GHCR packages are public, so Azure pulls them without registry credentials.
Alternatives considered: App Service (one plan always running, so it spends credit while idle). Azure Container Registry (costs per day; GHCR is free and already used by CI). A service principal with a client secret (IE accounts cannot create one, and a secret in GitHub would have to be rotated). Sending the connection string itself as one GitHub secret (the pipeline builds it from the password instead, so the host and database names stay visible in cd.yml and system.yaml and only the password is secret). The ingress CORS setting (it rejects the preflight of JSON POSTs). Pinning images by the latest tag (the SHA tag ties each revision to a commit, and /health shows it). A separate CI and CD run on main (CI would run twice and a deploy could start before its own commit had passed).
Consequences: Idle cost is close to zero, but the first request after a quiet period meets a cold container and possibly a paused database: about 30 s to a minute, during which Container Apps can answer 503. The services retry the database at startup for about 90 s and the UI shows "starting up" and retries reads, so this is visible but not an error. The images are public; they contain no secrets (configuration and passwords come from the environment). "Allow Azure services" on the SQL firewall lets any Azure-hosted client reach the server's login, so the protection is the per-service passwords. Rotating a database password means ALTER USER in that database, changing the GitHub secret and re-running CD. The SQL administrator password is only in my password manager and is not used by anything automatic. Rolling back means reverting the commit on main, which deploys the previous code as a new revision; migrations only go forward (ADR-7), so a revert must not depend on undoing one.

## 9. Pipeline and testing: what CI gates on, a stub and a compose test across the seam
Date: 2026-11-19
Status: Decided
Context: Every push and pull request must be linted, tested with at least 70% coverage per service, have its images built and its system description validated, and there must be at least one integration test across the seam. CI must never touch Azure SQL. ADR-4's tests used in-memory SQLite, which no longer matches production.
Decision: CI (.github/workflows/ci.yml) has four jobs and fails if any fails. (1) test, once per service: ruff, then pytest against a throwaway SQL Server container with a random password made in that run, failing under 70% coverage of the domain package, migrate.py and db.py; app.py is wiring and is exercised but not counted. The tests create their own batches_test / feedback_test database and apply the real migration files, so a broken migration fails CI. (2) describe: each openapi.yaml is validated against the OpenAPI specification; the services' own tests also check that every Flask route is in the document and nothing else, and that real responses match the documented schemas. (3) integration, against the compose stack (both real images, SQL Server, db/init.sql) with random passwords: a batch is created in batches, a report is sent to feedback, feedback must show the product it fetched from batches, then the test runs docker compose stop batches and checks that feedback still answers within 5 s with its own data and the notice, still accepts a report and still reports itself healthy. (4) images: both images are built after the other jobs pass. A newer push cancels the older run on the same branch. The cross-seam flow is tested at two levels: in feedback's unit tests batches is replaced by a stub (tests/stub_batches.py), a real HTTP server on a random local port, so the code goes through urllib, sockets and the timeout as in production, and the stub can be made slow, return 500 or return an HTML error page, which is hard to do with the real container on demand. The stub's answers are validated against services/batches/openapi.yaml, so the stub cannot silently drift from the real service. The compose test then checks the same flow with the real batches service and Docker DNS.
Alternatives considered: Only the stub, rejected because it cannot catch a wrong environment variable, a wrong service name in BATCHES_URL or a container that cannot reach the other on the compose network. Only the compose test, rejected because it is slow (building images and starting SQL Server) and cannot easily produce a slow or broken batches service. SQLite in tests, rejected because the SQL dialect differs (BIT, AVG of INT, IDENTITY) and the migrations are T-SQL. A GitHub Actions service container for SQL Server, equivalent; I kept docker run so the password can be generated in the same step.
Consequences: Deliberately not tested: the UI's JavaScript (no browser tests; it was checked by hand against the compose stack, including with batches stopped, because Playwright would add a Node toolchain for three small pages); Azure-only behaviour (cold starts, a paused database answering 40613), because CI never touches Azure: the retry logic has unit tests and the post-deploy health check covers the real thing; load and performance; and security scanning (bandit, safety from the class exercise), left out because ruff's bugbear rules plus pinned dependencies cover the obvious problems for two small services, and it is the first thing I would add. The CD workflow will reuse this workflow, so a deploy runs only if every gate above passed on the same commit (ADR-8).

## 10. Migration 002: recalling a batch, as an expand-only change to a table that already holds data
Date: 2026-11-21
Status: Decided
Context: By the time of the second migration, the batches database on Azure already held rows (the seed batches and batches added through the UI), so the change had to keep every existing row and run unattended in the pipeline (ADR-7). During a deploy, Container Apps keeps the previous revision serving until the new one is healthy, so for a short time old code runs against the new schema; a rollback (reverting the commit, ADR-8) also runs old code against it, because migrations only go forward. Staff also needed a way to pull a batch from sale without losing it, and Assignment 1 had no way to change or remove a batch.
Decision: 002_batch_recall.sql adds two NULL-able columns, recalled_on DATE and recall_reason NVARCHAR(200), and a check constraint, ck_batches_recall, that both are set or both are NULL. Existing rows get NULL in both, which already means "not recalled", so nothing is backfilled and the constraint holds for them when it is created (in a second batch after GO, because it names the new columns). Nothing is renamed or dropped, and the 001 code names its columns in every SELECT and INSERT, so the previous revision keeps working before, during and after the migration. The API grows the same way: POST /batches/{code}/recall (once per batch, with a reason), PATCH /batches/{code} for product, expires_on and quantity, and DELETE /batches/{code} for a batch registered by mistake. batch_code is never editable, because feedback stores it (ADR-6). In openapi.yaml the two new fields are optional in Batch, since a pre-002 revision answers without them; feedback does not read them and the UI treats a missing field as not recalled. status stays the expiry status, and recall is reported beside it rather than as a new status value, which feedback would not know how to show. /health on batches now also returns the last migration applied, so the CD log and a curl show which schema is live.
Alternatives considered: A NOT NULL recalled BIT with a default, rejected because the date and reason are still needed, the flag would duplicate "recalled_on IS NOT NULL", and a default constraint is one more object to manage. A separate recalls table, rejected because a batch is recalled at most once, so a 1:1 table only adds a join. Adding "recalled" to the status enum, rejected because it changes the contract feedback consumes (ADR-6) and mixes two independent facts: a recalled batch can also be expired. Renaming or tightening an existing column in the same release (expand and contract at once), rejected because the old revision would break during the rollout; a contract step would be a later migration, once no running code uses the old shape.
Consequences: The migration is safe to run with data and needs no downtime, but the schema now has two columns that are NULL for almost every row, and the "both or neither" rule lives in the database as well as in the code. Deleting a batch leaves its feedback in the feedback service, which then shows it without batch details (the same path as a code that was never registered); recall is the normal path and DELETE is meant for mistakes, but nothing stops staff from deleting a batch with feedback, and with a staff login (ADR-5) I would restrict it. Tested: a separate test database is migrated to 001 only, given rows, upgraded with the real migrations folder, and checked to keep its rows unchanged and to record 002 once; another test runs the 001 code's INSERT and SELECT after 002. On Azure the evidence is the CD log (batches healthy on the commit with schema 002_batch_recall.sql) and the batches that existed before the deploy still listed afterwards.
